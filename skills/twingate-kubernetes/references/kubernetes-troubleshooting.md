# Kubernetes Troubleshooting

## Summary
Diagnostic guide for when `kubectl` can't reach a cluster through Privileged Access for Kubernetes. It covers connection resets (Connector-to-Gateway reachability and TLS mismatches), kubeconfig sync failures, and known issues around session recording, `kubectl cp`, and ArgoCD.

## Key Information
- Connection reset with **no Gateway logs** plus **"DNS lookup failed"** in the Resource's network events means the Connector can't reach the Gateway.
- Connection reset with no Gateway logs plus a **successful connection lasting under 1 second** means the Client's TLS handshake with the Gateway failed.
- If the Resource has an alias, the synced kubeconfig uses the alias, so the Gateway certificate must cover it.
- The Gateway records `kubectl exec` and similar sessions only over WebSocket. Sessions that fall back to SPDY are not recorded.

## Prerequisites
- Signed in to the Twingate Client.
- Kubeconfig synced (manually if autosync is off).
- Access to Gateway logs and the Admin Console (Resource network events).

## Step-by-Step: First Checks
1. Sign in to the Client. If autosync is off, run `twingate kube config sync`.
2. Switch to the context the Client added and run `kubectl config view --minify --output yaml`.
3. Run `kubectl auth whoami`.
4. Check the Gateway logs. No entries means the request never reached the Gateway.
5. Check the Resource's network events in the Admin Console.

### Diagnose TLS mismatch
From a machine running the Client:
- `curl -k -v https://kubernetes.default.svc.cluster.local`
- `curl -k -v https://my-k8s-cluster.int` (the alias)

If the alias test fails, the Gateway certificate doesn't include the alias.

## Configuration Values
- `twingateOperator.gateway.address`: set when Connectors reach the Gateway via NodePort, ingress, proxy, or private endpoint (Gateway 2.1+).
- `tls.certificates.autoGenerated.dnsNames`: add the alias here in the Gateway Helm values.
- `twingateOperator.kubernetesResource.alias`: automatically added to the certificate.
- `twingateOperator.gateway.certificateAuthority.name`: must be set manually under ArgoCD.
- `KUBECTL_REMOTE_COMMAND_WEBSOCKETS`, `KUBECTL_PORT_FORWARD_WEBSOCKETS`: disabling these forces SPDY.
- Feature gates for 1.29/1.30 clusters: `TranslateStreamCloseWebsocketRequests` (1.29+), `PortForwardWebsockets` (1.30+).

## Gotchas
- **ClusterIP with external Connectors:** the default `ClusterIP` service is reachable only inside the cluster, and any Connector in the Remote Network may carry the connection. Expose the Gateway with a `LoadBalancer` service, or set `twingateOperator.gateway.address`.
- **CA mismatch:** the CA certificate in the Resource configuration must match the Gateway's TLS certificate.
- **`~/.kube` missing:** the Client can't sync. Create the folder and sync again.
- **macOS permission denied:** the Client is running as `root` (home `/var/root`), often when installed via MDM. Run it as the signed-in user. Check with `ps aux | grep '[T]wingate.app'`.
- **SPDY fallback:** clusters or `kubectl` on 1.28 or earlier always use SPDY. 1.31+ uses WebSockets by default.
- **`kubectl cp` on large files:** use `kubectl cp --retries` (Kubernetes issue #60140).
- **ArgoCD:** Helm's `lookup` returns nothing, so the default auto-generated certificate is regenerated on every sync (ArgoCD issue #5202). Use cert-manager or your own certificate.
