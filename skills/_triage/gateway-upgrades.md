# Upgrading the Gateway

## Summary
Lists configuration file and Helm value changes between major Gateway versions (0.21 → 1.0 → 2.0 → 2.1) and whether each affects you. Full before/after migration guides live in the Gateway GitHub wiki. If the Gateway is a subchart of the Twingate Kubernetes Operator, the Helm values sit under the `gateway:` key (Operator v3 bundles Gateway 2.0).

## Key Information
- **2.1** (from 2.0): no config or Helm changes required.
  - New optional `twingateOperator.gateway.address` (`host`, `port`) registers an explicit address (for proxy, ingress, NodePort, private endpoint). Needs Operator 3.1.0+.
  - HTTP/2 is now supported for Kubernetes and Web App connections.
  - The Gateway returns `421 Misdirected Request` when a request's host doesn't belong to the Resource.
  - `X-Forwarded-Proto` now reflects client TLS.
- **2.0** affects you if you set: config `tls`, `ssh.ca.manual`, `auditLog`, `cas`; Helm `tls`, `ssh.ca`, `auditLog`, `TWINGATE_DEBUG`; or the `--debug`/`-d` flag; or log filters on `gateway.audit`.
- **1.0** affects you if Helm values set `twingate.resource.*` (including installs that followed the Operator setup).

## Prerequisites
- For 1.0: Twingate Kubernetes Operator v2 with CRDs applied (`twingateOperator.gateway.enabled=true`). Follow the Operator v1→v2 migration guide first.
- For 2.0 Vault bundle: create the ConfigMap (key `ca.crt`) before upgrading.

## Step-by-Step (migration changes)
**2.0 TLS**
- Config: `tls.certificateFile`/`privateKeyFile` → entry in `tls.certificates.files`.
- Helm: `tls.dnsNames`, `ipAddresses`, `autoGenerated` → `tls.certificates.autoGenerated`. `tls.existingSecret` and inline `cert`/`key`/`ca` → `tls.certificates.secrets`. `tls.autoGenerated: true` boolean is removed.

**2.0 SSH CA**
- `ssh.ca.manual` → `ssh.ca.local`; `manual.existingSecret` → `local.secretName`.
- `vault.existingCABundleSecret` → `vault.caBundleConfigMapName`.
- `vault.auth.appRole.existingSecretIdSecret` → `secretIdSecretName`.
- `vault.auth.token` and `existingTokenSecret` removed; use `VAULT_TOKEN` via `extraEnvVars` with `secretKeyRef`.

**2.0 Debug logging**
- Remove `--debug`, `-d`, `TWINGATE_DEBUG`; set `log.system.level: debug`.

**2.0 Session recording**
- `auditLog.flushInterval` → `log.sessionRecording.segment.maxDuration`.
- `auditLog.flushSizeThreshold` → `log.sessionRecording.segment.maxSize` (quoted string, e.g. `"64KiB"`).
- Logger name `gateway.audit` → `session_recording`.

**2.0 Upstream CA bundles** (config file, from 1.1): `cas` → `upstreamTrustedCABundles`; `certFile` → `file`; `name` removed.

**1.0**
- Move `twingate.resource.*` to `twingateOperator.gateway.*` and `twingateOperator.kubernetesResource.*` (annotations `resource.twingate.com/name`/`alias` become `name`/`alias`).
- Other `TwingateResource` spec fields (e.g. `securityPolicyId`) can be set under `kubernetesResource`. The chart owns `type`, `address`, `gatewayRef`; the Remote Network comes from `twingateOperator.remoteNetworkId`.

## Configuration Values
- `tls.certificates.autoGenerated.enabled`, `.dnsNames`
- `log.system.level`
- `log.sessionRecording.segment.maxDuration` / `maxSize`
- `twingateOperator.gateway.certificateAuthority.name`
- `twingateOperator.kubernetesResource.name`

## Gotchas
- Setting `tls.certificates.secrets` no longer disables auto-generation; set `autoGenerated.enabled: false` to supply all certs.
- Auto-generated cert and CA are reissued on upgrade; anything pinning the old CA must trust the new one.
- In-cluster Kubernetes names are added only when the Kubernetes proxy is enabled; list other names in `autoGenerated.dnsNames` or the release fails to render.
- `certManager.commonName` is omitted unless set.
- `VAULT_TOKEN` applies to all Vault clients (SSH CA and TLS); use AppRole for one to separate credentials.
- Starting with `--debug` fails in 2.0.
- `maxSize` default drops from 1MB to 64KiB, capped at 256KiB.
- 1.0: if no display name was set, the Admin Console name changes from `<fullname>-resource` to `<fullname> Kubernetes cluster`; set `kubernetesResource.name` to keep it. Access is unchanged.
- 1.0: CA is registered as `<fullname>-ca-<hash>`; the hash needs Kubernetes API access at render time. With ArgoCD, `helm template`, or `--dry-run=client`, set `certificateAuthority.name` manually (must be unique and can't be changed later).
