# Gateway TLS Certificates

## Summary
The Twingate Gateway serves a TLS certificate that must be valid for every address and alias of every Resource it serves. Certificates can be static (auto-generated, cert-manager, or user-supplied) or on-demand (signed during the handshake by a Local CA, HashiCorp Vault, or Google Cloud Private CA). Examples use the Twingate Kubernetes Operator Helm chart (Gateway 2.0 values, bundled from Operator v3), where the Gateway lives under the `gateway:` key.

## Key Information
- **Selection order per handshake:** (1) the first static certificate valid for the SNI (auto-generated is checked first, then `tls.certificates.secrets` in order); (2) if none match and on-demand is configured, the cached or newly signed on-demand certificate; (3) otherwise the first static certificate.
- **Static certs** are reloaded when the files change (e.g. cert-manager renewal).
- **On-demand certs:** one per SNI, so a Resource reached by both address and alias gets two. The handshake is held while the issuer signs (can take a few seconds). If signing fails, the handshake fails. There is no background renewal; a cert within 5 minutes of expiry is replaced on the next handshake.
- Wildcards match exactly one label: `*.svc.cluster.local` does not cover `billing.default.svc.cluster.local`, and `*.acme.int` does not cover `acme.int`.
- In Gateway 1.x, `dnsNames` and `ipAddresses` sat directly under `tls`.

## Prerequisites
- Gateway installed via the Twingate Operator Helm chart (or equivalent values)
- For cert-manager: an existing Issuer or ClusterIssuer
- For Vault: PKI secrets engine and AppRole auth
- For GCP: a CA pool in Certificate Authority Service

## Step-by-Step
Apply changes with:
`helm upgrade twop oci://ghcr.io/twingate/helmcharts/twingate-operator --install --wait -f ./values.yaml`

**Vault issuer:**
1. Enable PKI and generate a root CA.
2. Create a PKI role (`gateway-tls`) with allowed domains, `allow_subdomains=true`, `require_cn=false`.
3. Create an AppRole and save the role ID and secret ID.
4. Write a policy allowing `create`/`update` on `pki/sign/gateway-tls` and attach it to the AppRole.
5. Read the root CA with `vault read -field=certificate pki/cert/ca`.
6. Add the values to Helm.

**GCP Private CA issuer:**
1. Grant `roles/privateca.certificateRequester` on the pool to the Gateway's identity (Workload Identity on GKE, or the VM service account on Compute Engine).
2. Fetch root CA certs with `gcloud privateca pools get-ca-certs`.
3. Add to Helm values.

## Configuration Values
- `gateway.tls.certificates.autoGenerated.enabled`, `.dnsNames`, `.ipAddresses`
- `gateway.tls.certificates.autoGenerated.certManager.enabled`, `.issuerRef.name`, `.issuerRef.kind`
- `gateway.tls.certificates.secrets[]`: `name`, or `cert`/`key`/`ca`
- `gateway.tls.automation.enabled`
- `gateway.tls.automation.certificate.commonName`
- `gateway.tls.automation.issuer.local.certificate` / `.privateKey`
- `gateway.tls.automation.issuer.vault`: `address`, `auth.appRole.roleId`, `secretId` or `secretIdSecretName`, `role`
- `gateway.tls.automation.issuer.gcpPrivateCA`: `project`, `location`, `caPoolId`
- `gateway.twingateOperator.gateway.certificateAuthority.certificate` (CA registered with Twingate for Vault/GCP)

## Gotchas
- Setting `secrets` does not disable the auto-generated cert; also set `autoGenerated.enabled: false` to supply all certs yourself.
- Auto-generated certs under ArgoCD, `helm template`, or `--dry-run=client` regenerate the CA and cert on every sync (Helm `lookup` returns nothing). Use cert-manager or your own cert.
- Vault: the Gateway sends no CN unless `commonName` is set, so the role needs `require_cn=false`. It sends `exclude_cn_from_sans=true` and rejects certs whose SANs differ from those requested.
- Use `secretIdSecretName` (a Kubernetes Secret with key `secretId`) in production; inline `secretId` is for testing only.
- GCP issuer requires `commonName`.
- **IP connections:** clients dialing an IP send no SNI. With static certs, the first static cert is served; with only on-demand, a cert with no SANs is served and rejected. Fix by using an alias, or make the first static cert cover the IP.
